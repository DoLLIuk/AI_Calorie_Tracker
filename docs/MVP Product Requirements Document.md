AI Diet Coach — Design Document (MVP)
Версия 1.1 · iOS + Android · Мобильный AI-коуч по питанию

Изменения в v1.1:
• Переструктурирован документ, удалены повторяющиеся фрагменты, улучшена читаемость.
• Расширена секция монетизации: добавлены триггеры оплаты, оффер −50% на первый месяц, streak-механики.
• KPI/метрики вынесены в отдельную секцию.

0. Актуальный статус реализации (as-is, на текущий момент)
Важно: разделы ниже (монетизация, пуш-расписание, paywall, расширенные флоу) сохраняются как продуктовый план. Этот блок фиксирует текущее поведение приложения, чтобы не было расхождений.

0.1 Реализовано сейчас
• Onboarding с сохранением draft и итогового результата: цель, пол, возраст, рост, вес, активность, темп, макропрофиль.
• Домашний экран: прогресс калорий и макросов, Latest Added, история по категориям Breakfast/Lunch/Dinner/Snacks.
• Добавление еды: камера / галерея / ручной ввод.
• Ручной ввод: полная форма (название, ккал, граммы, Б/Ж/У, тип приема пищи).
• Редактирование и удаление записей; при изменении граммов КБЖУ пересчитываются пропорционально.
• Локальное хранение через SharedPreferences (onboarding + meals).
• Профиль и App Preferences: UI-экран настроек, редактирование профиля через существующий onboarding (режим редактирования, не с нуля), подтверждение на Log Out.

0.2 Фото/AI-флоу (фактическое поведение)
• Используется multipart-загрузка изображения на backend endpoint `POST /v0/ai/photo-food`.
• Подтверждение порции: `POST /v0/ai/photo-food/confirm-portion`.
• Текущая клиентская логика НЕ применяет локальные пороги confidence (типа “<0.30 всегда не показывать результат”).
• Решение о дополнительном подтверждении принимает backend; клиент обрабатывает ответ и, при необходимости, открывает flow подтверждения порции.
• При ошибках (например, нераспознаваемое фото/сеть/таймаут) показывается сообщение и доступен fallback на повтор/ручной ввод.

0.3 Что в документе ниже пока план, а не текущее поведение приложения
• Free/Premium ограничения, paywall и подписка.
• Пуши по расписанию и расчеты X ккал в уведомлениях.
• Экономичный direct-to-storage (presigned upload) pipeline.
• Расширенная история “за месяц” по подписке.

1. Краткое описание
AI Diet Coach — мобильное приложение-диетолог/коуч для спорт-питания с сильным кейсом похудения. Приложение помогает структурировать питание (когда и сколько есть) и дает контроль КБЖУ и калорий через дневник питания (фото/вручную) и пуш-уведомления.
2. Проблема
Пользователю сложно:
соблюдать режим питания
понимать калории и макросы по дню и по неделе
не тратить деньги на диетолога ради базовой структуры и контроля
3. Цели MVP
Быстро и удобно логировать еду (целевой сценарий: до 20 секунд на добавление).
Видеть итоги дня (калории + Б/Ж/У) и список приёмов пищи.
Получать мягкие пуш-напоминания по расписанию, включая оценку остатка калорий на текущий прием.
Чёткая граница Free vs Premium.
Вне MVP (out of scope):
трек воды, трек веса
медицинские планы, работа с аллергиями/заболеваниями/беременностью (только дисклеймер)
умная адаптация расписания по календарю/поведению
4. Целевая аудитория
Студенты и молодые взрослые до ~30 лет.
Основные сегменты:
Спорт/зал: набор или поддержание, важна структура и белок.
Похудение: дефицит и дисциплина, важна история и контроль калорий.
5. Ценность продукта (Core Value)
Фото/ручной ввод еды -> калории и КБЖУ.
Структура дня: напоминания о приемах пищи (мягкий коуч).
История питания по дням (в Free — ограниченная, в Premium — расширенная).
6. Объем MVP (Scope)
6.1 Must-have (обязательно)
Onboarding: рост, вес, пол, возраст, цель (похудение/поддержание/набор).
Расчёт целей на день: калории и макросы (Б/Ж/У).
Главный экран «Сводка дня»: текущие калории и Б/Ж/У + список недавней еды.
Дневник питания: прием пищи = набор позиций (MealItems).
Добавление еды: по фото + выбор порции (граммы или S/M/L) и ручной ввод.
Редактирование и удаление приемов и позиций.
Пуш-уведомления по расписанию с подсказкой «сколько осталось на приём».
История (Free): сегодня + вчера; Premium: история за месяц.
6.2 Nice-to-have (после MVP)
Пояснение «почему рекомендовано» (например, про белок/дефицит).
Графики/календарь, streak, достижения.
Рекомендации блюд/рецептов.
Адаптивное расписание.
7. Основные пользовательские сценарии
7.1 Первый запуск
Дисклеймер и согласие.
Анкета: рост, вес, пол, возраст.
Выбор цели: похудение / поддержание / набор.
Показ рассчитанных целей (ккал + Б/Ж/У).
Предложение настроить расписание приёмов пищи (можно пропустить).
Короткий гайд по экранам: «Сводка дня», «Добавить еду», «История».
7.2 Ежедневный цикл
Пуш: «Рекомендуем поесть. На этот приём пищи осталось ~X ккал…».
Добавление еды (фото или вручную).
Обновление сводки дня (ккал + Б/Ж/У) и списка недавней еды.
Просмотр итогов дня/вчера в истории.
8. Экраны и UI-спека (MVP)
Ниже приведён перечень экранов и ключевых компонентов/состояний.
8.1 Splash / Loading
Авто-логин, проверка подписки, подготовка дневного лога.
Состояния: loading / error (retry).
8.2 Onboarding
Дисклеймер + согласие.
Анкета (пол, возраст, рост, вес) + валидация.
Цель (cut/maintain/bulk).
Экран результата расчёта: цели ккал и Б/Ж/У.
CTA: «Настроить расписание» / «Пропустить».
8.3 Настройка расписания
Переключатель «Включить расписание».
Количество приёмов пищи по умолчанию: 4–5 (с перекусами).
Слоты с time picker (завтрак/перекусы/обед/ужин).
Запрос разрешений на уведомления (если не выданы).
8.4 Настройка порций S/M/L
Дефолт: S=150г, M=250г, L=350г.
Настройки позволяют изменить граммы для S/M/L.
8.5 Главный экран: «Сводка дня»
Карточка: калории (Eaten/Target) + статус (осталось/перебор).
Карточка: Б/Ж/У (Eaten/Target).
Список «Недавняя еда»: время + название + ккал, тап -> редактирование приёма.
CTA: «Добавить еду».
Состояния: пустой день; лимит фото исчерпан; ошибки сети.
8.6 Добавить еду
Опции: камера / галерея / ручной ввод.
Если лимит фото исчерпан (Free) -> предложить ручной ввод или Premium.
8.7 Фото-флоу (1 результат)
Preview фото -> «Далее».
Выбор порции: граммы или S/M/L.
Запрос к AI -> один результат (название + нутриенты на 100г + confidence).
Экран подтверждения: «Добавить» / «Исправить вручную».
Ошибки: IMAGE_UNCLEAR или timeout -> retry или ручной ввод.
8.8 Ручной ввод
Ввод текста (например, «гречка»), выбор порции (граммы или S/M/L), «Рассчитать».
Если распознано -> подтверждение и добавление.
Если не распознано -> пользователь вводит калории и Б/Ж/У вручную.
8.9 Экран приёма пищи (Meal detail)
Приём пищи содержит набор позиций (MealItems).
Редактирование: время, граммы, значения КБЖУ, удаление позиций.
Итог по приёму: ккал и Б/Ж/У.
Удаление приёма пищи.
8.10 История
Free: сегодня + вчера.
Premium: история за месяц (список дат или календарь).
Попытка открыть недоступные дни в Free -> paywall.
8.11 Paywall
Преимущества Premium: безлимит фото, история за месяц, полное расписание.
Цена: $10/мес.
CTA: «Оформить подписку», «Восстановить покупки».
8.12 Настройки
Порции S/M/L (граммы).
Расписание приёмов пищи (вкл/выкл, времена).
Уведомления (ссылка в системные настройки при запрете).
Подписка (статус/restore).
Дисклеймер.
9. Монетизация, ограничения и триггеры оплаты
Цель: простая и прозрачная граница Free vs Premium + paywall в моменты, когда пользователь уже почувствовал ценность (логирует еду, строит серию, упирается в лимит, хочет историю).
9.1 Free
• 5 фото-анализов в день.
• История: сегодня + вчера.
• Расписание: облегчённая версия (ограничение по функционалу).
9.2 Premium ($10/мес)
• Безлимит фото-анализов.
• История за месяц (неделя/месяц, тренды).
• Полная версия расписания + расширенные пуши по приёмам пищи.
9.3 Intro offer: −50% на первый месяц
Механика: скидка доступна ограниченное время, чтобы снизить барьер первой оплаты и ускорить конверсию.
Рекомендованный вариант для MVP:
• Скидка −50% на первый месяц действует 24 часа с момента активации оффера.
• Если пользователь не купил — оффер скрывается на 7 дней (чтобы не обесценивать подписку).
Точки показа оффера:
• После «первого успешного дня»: ≥2 приёма пищи или ≥3 фото за день.
• На первом упоре в лимит (попытка сделать 6-е фото).
9.4 Триггеры оплаты (paywall moments)
Триггер A — Лимит фото (самый прямой):
• 1–4 фото: показываем мягкий счётчик «осталось N фото сегодня».
• 5-е фото: «последнее бесплатное фото на сегодня».
• 6-е фото: paywall (с акцентом «не теряй день/прогресс») + приоритетно показываем −50% оффер, если доступен.
Триггер B — История и прогресс:
• Free видит только сегодня/вчера. При попытке открыть «Неделя/Месяц» показываем paywall.
• Рекомендуемая точка: начиная с 3-го дня использования или после 3–5 логирований.
Идея: пользователь платит за доступ к уже накопленным данным (самый «честный» мотив оплаты).
Триггер C — Streak (серии) по белку/калориям:
Смысл: человек не хочет «сбить серию», когда уже есть прогресс.
• Protein streak: засчитывается, если protein_today ≥ 90% от цели белка.
• Calories streak: засчитывается, если calories_today в пределах цели (например ±5%).
Показы paywall:
• На 3-й день серии (первый сильный момент).
• На 7-й день серии (второй сильный момент).
Анти-токсичность streak:
• Допуск: 1 «пропуск» в неделю без обнуления серии (или «серия продолжается при логировании хотя бы 1 приёма пищи»).
• Если день пропущен — мягкое сообщение без давления, без продажи через чувство вины.
9.5 Шаблоны текстов paywall (MVP)
Paywall (лимит фото):
Заголовок: «Безлимит фото-анализов»
Подзаголовок: «Ты уже ведёшь дневник. Не теряй день — включи Premium и логируй всё питание.»
CTA: «Перейти на Premium» / «Активировать −50%» (если оффер доступен).
Paywall (история):
Заголовок: «Посмотри прогресс за неделю»
Подзаголовок: «В бесплатной версии доступно только сегодня и вчера. В Premium — история за месяц и тренды.»
CTA: «Открыть историю в Premium»
Paywall (streak):
Пример: «Ты добираешь белок уже 3 дня подряд 🔥 Не сбивай серию — в Premium безлимит фото и полный контроль прогресса.»
10. Логика пушей (MVP)
Текст пуша: «Рекомендуем поесть. На этот приём пищи осталось ~X ккал для достижения цели.»
Простая формула расчёта X:
remaining_day = target_day - eaten_today
meals_left = количество оставшихся слотов сегодня (включая текущий)
X = max(0, remaining_day / meals_left)
Photo Core v1 (Upload → AI → Confirm → Log)
Цели
Быстро добавлять приём пищи по фото с минимальным трением.


Всегда иметь понятный fallback на ручное исправление при низкой уверенности.


Сделать загрузку фото и вызов AI максимально экономичным по инфраструктуре и трафику.


MVP-ограничения
На фото предполагается 1 основное блюдо (dominant dish).
Пользователь обязательно задаёт порцию: граммы (или S/M/L, если включим позже).
При очень низкой уверенности мы не убеждаем, а сразу ведём в ручное исправление.



Стратегия загрузки и хранения фото (ориентир на экономию)
Решение: Direct-to-Object-Storage (presigned upload)
Чтобы снизить стоимость (трафик/CPU на бэкенде) и упростить масштабирование, фото загружается напрямую в object storage по presigned URL.
Поток:
Клиент запрашивает presign на бэкенде


Бэкенд выдаёт upload_url и photo_id


Клиент делает PUT в object storage


Клиент вызывает AI-распознавание уже по photo_id (без передачи бинарника через бэкенд)


Правила подготовки изображения (MVP)
Клиент сжимает/уменьшает фото перед загрузкой (таргет: max side ~1600px, размер по возможности <= 1.5MB).


На стороне бэкенда/хранилища храним:


original (опционально; можно отключить позже)


normalized_preview (рекомендуется для стабильного инференса и UI)



AI Photo Recognition (контракт v1)
Запрос распознавания
Endpoint: POST /ai/photo-food
Поля запроса (минимум для MVP):
photo_id
portion:
type = "grams"
value_g (например 200)
context (опционально):
meal_time (breakfast/lunch/dinner/snack)
locale (например ru-RU)



Ответ AI (контракт v1)
item (результат распознавания)
name — название блюда
category — крупная категория (опционально, но добавляем)
food_type — тип/подтип (опционально, но добавляем)
confidence — уверенность [0..1]
serving_suggestion_g — рекомендация порции в граммах (может быть null в MVP)
nutrition_per_100g — КБЖУ на 100г
warnings[] — массив предупреждений (например LOW_CONFIDENCE и т.п.)
ui_flags (для UI и бизнес-логики)
Добавляем блок:
requires_user_confirmation — флаг “нужно ли явно попросить пользователя проверить результат”
highlight_level — уровень подсветки UI: none | orange | critical
Смысл requires_user_confirmation:
false — можно показывать результат “спокойно” (CTA: “Добавить”)
true — нужно “попросить подтвердить” (подсветка/баннер + CTA: “Подтвердить и добавить”, рядом “Исправить”)



Confidence → UX правила (MVP)
1) High confidence
Условие: confidence >= 0.60
UI:
показываем результат без проблем
requires_user_confirmation = false
highlight_level = none
основной CTA: “Добавить”
2) Medium confidence
Условие: 0.30 <= confidence <= 0.59
UI:
показываем результат, но с оранжевой задней панелью за текстом (подсветка)
requires_user_confirmation = true
highlight_level = orange
CTA: “Подтвердить и добавить”
secondary: “Исправить вручную”


3) Low confidence
Условие: confidence < 0.30
UI:
сообщение: “Мы не уверены, что это. Можете исправить вручную.”
requires_user_confirmation = true
highlight_level = critical
основной путь: ручное исправление (поиск/выбор из каталога или ввод)



Ошибки и исключения (MVP)
AI endpoint возвращает структурированную ошибку с code и message.
Коды ошибок:
IMAGE_UNCLEAR — фото размыто/темно/пересвет
NO_FOOD_DETECTED
TIMEOUT
RATE_LIMIT
INTERNAL_ERROR
Поведение UI:
показывать понятное сообщение пользователю
предлагать повторить или перейти на ручной ввод

Кэширование (D)
Кэш по image_hash
После нормализации вычисляем image_hash (например sha256 по нормализованным байтам).


Если такой hash уже есть — повторно не гоняем AI, а возвращаем сохранённый результат (если пользователь не запросил “переоценить”).



Источник правды по нутриентам (E)
Правило:
Если распознанное блюдо матчится с Food Catalog → берём nutrition_per_100g из каталога как источник правды.


Если матча нет → принимаем nutrition_per_100g от AI, но сохраняем как draft/candidate (чтобы позже можно было нормализовать и пополнить каталог).



Телеметрия (обязательно для улучшения “кора”)
Для каждого распознавания сохраняем:
request_id, user_id, photo_id, image_hash


predicted_name, category/food_type, confidence


входная порция


latency_ms, error_code (если есть)


действие пользователя:


accepted_as_is / edited_manually / cancelled


финальное название и источник нутриентов (catalog / ai_draft)
11. Модель данных (MVP)
Базовые сущности:
User
MealPlanSettings
DayLog
Meal
MealItem

Ключевые правила:
Приём пищи (Meal) = набор позиций (MealItems).
Порция S/M/L хранится как граммы после конвертации (на основе настроек пользователя).
Для каждой позиции храним nutrition_per_100g и nutrition_total (итог на порцию).

12. API (черновик)
POST/GET /user — профиль и цели.
PATCH /settings — расписание и пресеты порций S/M/L.
GET /daylog?date=YYYY-MM-DD — сводка дня + список приёмов и позиций.
GET /history?from=...&to=... — история (ограничения по подписке).
POST/PATCH/DELETE /meal — CRUD приёмов пищи.
POST/PATCH/DELETE /item — CRUD позиций в приёме.
POST /ai/photo-food — распознавание по фото.
POST /ai/text-food — распознавание по тексту.

14. Edge cases и ошибки
Плохое фото -> retry или ручной ввод.
Низкий confidence -> показывать предупреждение и кнопку «Исправить».
Редактирование прошлых дней -> пересчёт итогов DayLog.
Смена дня по таймзоне -> daylog по локальной дате пользователя.

18. Самый важный чек‑лист метрик для MVP
Если эти цифры не сходятся — монетизация почти точно не взлетит. Минимальные ориентиры:
• D1 retention: 25–35%+
• D7 retention: 10–15%+
• Конверсия в trial/pay: 2–5%+ от активных пользователей.
• Churn в первый месяц: чем ниже, тем лучше (если «массовый отвал» — подписка не держится).
