# AI Food Logger — Product Requirements Document (MVP)

Версия 1.0 · iOS + Android · Узкий MVP для быстрого логирования еды

## 1. Назначение документа

Этот PRD описывает реальный MVP продукта, который уже близок к рабочему состоянию.

Цель документа:
- зафиксировать, что именно является продуктовым ядром;
- убрать из MVP лишние ожидания;
- отделить текущую ценность от будущих идей.

Этот документ intentionally уже, чем предыдущий продуктовый документ. Всё, что не помогает пользователю быстро и регулярно логировать еду, считается post-MVP, пока не доказана ценность основного сценария.

## 2. Продуктовая формулировка

AI Food Logger — это приложение, которое делает логирование еды достаточно быстрым и простым, чтобы пользователь мог делать это каждый день.

Основное обещание продукта:

`Сфотографируй еду или введи её вручную -> сразу получи калории и КБЖУ -> пойми, как идёт день относительно своей цели.`

Это не полноценный "AI-коуч" в рамках MVP.
В MVP продукт в первую очередь решает задачу удобного учёта питания, а не задачу глубокой мотивации, длинной аналитики или сложного персонального сопровождения.

## 3. Проблема пользователя

Пользователю сложно регулярно считать калории и макросы, потому что:
- это долго;
- ручной ввод раздражает;
- сложно быстро понять, как текущий приём пищи влияет на весь день;
- многие трекеры дают слишком много интерфейса и слишком мало ясности.

## 4. Целевая аудитория

Основная аудитория:
- люди, которые хотят следить за калориями и БЖУ без лишней сложности;
- пользователи с целями похудения, поддержания или набора;
- пользователи, которым нужен практичный инструмент, а не “виртуальный наставник”.

Наиболее вероятные ранние сегменты:
- зал / фитнес;
- снижение веса;
- дисциплина питания без работы с диетологом.

## 5. Главный пользовательский сценарий

Пользователь:
1. проходит onboarding;
2. получает личную цель по калориям и макросам;
3. в течение дня быстро добавляет еду через фото или вручную;
4. сразу видит, сколько уже съедено и сколько осталось;
5. при необходимости редактирует запись;
6. возвращается к приложению, чтобы продолжить вести день.

## 6. Core Value Loop

Основной цикл MVP:

`Добавил еду -> увидел прогресс дня -> понял следующий шаг -> добавил следующую еду`

В MVP этот loop важнее, чем:
- сложный коучинг;
- подписка;
- геймификация;
- глубокая история и тренды.

## 7. Цели MVP

### Основные цели

- Сделать добавление еды быстрым и понятным.
- Дать пользователю мгновенную обратную связь по калориям и КБЖУ.
- Сделать дневную картину читаемой без перегруза.
- Проверить, готовы ли пользователи возвращаться к продукту несколько дней подряд.

### Что нужно доказать

- Пользователь понимает продукт уже в первый день.
- Фото-флоу или ручной ввод реально экономят время.
- Пользователь ведёт хотя бы несколько приёмов пищи, а не бросает после первого.
- Дневная сводка достаточно полезна, чтобы к ней возвращаться.

## 8. In Scope (MVP)

### 8.1 Onboarding

- ввод базовых данных пользователя;
- выбор цели: похудение / поддержание / набор;
- расчёт дневной цели по калориям и КБЖУ;
- сохранение draft и итогового результата.

### 8.2 Home / Summary

- дневной прогресс калорий;
- дневной прогресс Б/Ж/У;
- список приёмов пищи за выбранный день;
- latest added / последняя добавленная еда;
- простой coach block как вспомогательная подсказка.

Coach block в MVP:
- короткий;
- контекстный;
- не центральное обещание продукта;
- не отдельный сценарий и не отдельный экран.

### 8.3 Логирование еды

- добавление еды через фото с AI-анализом;
- добавление еды из галереи;
- ручное добавление еды;
- подтверждение порции, если это требует backend;
- редактирование и удаление записи;
- пересчёт КБЖУ при изменении граммов.

### 8.4 История

- просмотр истории по дням в простом виде;
- категории приёмов пищи: Breakfast / Lunch / Dinner / Snacks;
- группировка по сессиям, если она помогает чтению дневника и не создаёт лишнего когнитивного шума.

История в MVP должна быть полезной, но простой.
Она не обязана становиться отдельным сложным аналитическим продуктом.

### 8.5 Локальное сохранение

- onboarding сохраняется между запусками;
- meal log сохраняется между запусками;
- пользователь не теряет данные при обычном повседневном использовании одного устройства.

## 9. Out of Scope (не MVP)

Следующие вещи не считаются обязательными для первой рабочей версии:

- полноценный AI coach как основная продуктовая роль;
- сложные insights и аналитика по неделям/месяцам;
- streak mechanics;
- paywall triggers по нескольким событиям;
- intro-offer `-50%`;
- полноценная подписка и биллинг;
- free/premium сегментация как обязательная часть первого запуска;
- адаптивное расписание;
- рецепты, рекомендации блюд;
- water tracker;
- weight tracker;
- медицинские сценарии;
- 2FA, пароль, “аккаунтность” без реальной backend-account системы.

## 10. UX-принципы MVP

- Быстрее важнее, чем “умнее”.
- Ясность важнее, чем количество функций.
- Пользователь должен понимать статус дня за несколько секунд.
- Если AI не справился, fallback на ручной сценарий должен быть очевидным.
- Приложение не должно создавать ложное ожидание функций, которых ещё нет.

## 11. Экранный состав MVP

### 11.1 Splash / Loading

- гидратация локального состояния;
- переход в onboarding или основной shell.

### 11.2 Onboarding

- базовая анкета;
- цель;
- результат расчёта.

### 11.3 Home

- калории;
- Б/Ж/У;
- coach hint;
- latest added;
- список дневных записей;
- CTA на добавление еды.

### 11.4 Add Meal

- камера;
- галерея;
- ручной ввод.

### 11.5 Meal Edit

- изменение записи;
- изменение граммов;
- изменение типа приёма пищи;
- удаление.

### 11.6 Profile / Settings

Только реально работающие настройки.

Если какая-то настройка не подключена к реальной логике продукта, её не должно быть в MVP-интерфейсе.

## 12. Нефункциональные требования MVP

- приложение должно стабильно запускаться без сети, если пользователь уже проходил onboarding;
- локальные данные должны восстанавливаться после перезапуска приложения;
- ошибки AI-флоу должны иметь понятный fallback;
- добавление еды не должно ощущаться как длинный и хрупкий процесс.

## 13. Метрики успеха

### Primary metrics

- onboarding completion rate;
- first meal logged rate;
- meals logged per active day;
- day-2 retention;
- day-7 retention;
- photo flow completion rate;
- manual fallback rate.

### Operational metrics

- median time to log one meal;
- photo analysis failure rate;
- edit/delete usage rate;
- percentage of users who log more than one meal in first day.

## 14. Гипотезы MVP

- Пользователи готовы регулярно логировать еду, если это быстрее и проще, чем в обычных calorie trackers.
- Фото-флоу повышает вероятность первого успешного логирования.
- Даже простой day summary уже даёт достаточно пользы без сложных графиков.
- Лёгкий coach hint может усилить ясность, но не является обязательным driver ценности.

## 15. Риски

### Продуктовые риски

- пользователю может быть удобнее просто ручной ввод, чем AI-фото;
- ценность может быть в разовом использовании, а не в регулярной привычке;
- дневная сводка может быть полезной, но недостаточной для возврата.

### UX-риски

- если AI ошибается слишком часто, пользователь теряет доверие;
- если в интерфейсе есть неработающие настройки, это разрушает ощущение качества;
- если история или session logic выглядят слишком сложными, продукт перестаёт быть “простым”.

### Бизнес-риски

- слишком раннее внедрение монетизации может испортить обучение на ранних пользователях;
- без аналитики невозможно понять, что именно работает, а что нет.

## 16. Post-MVP / Future Goals

Следующие темы допустимы только после подтверждения core loop:

- push reminders;
- premium / subscription;
- photo limits;
- extended history;
- streak mechanics;
- deeper insights;
- coach system как отдельный retention layer;
- облачная синхронизация / аккаунты;
- монетизация и paywall strategy.

Подробные идеи по этим направлениям вынесены в отдельный документ:

`docs/Future Product Goals.md`

## 17. Решение по стратегии

Стратегия MVP:

`Не строить сразу "AI diet coach". Сначала доказать ценность узкого продукта для ежедневного логирования еды.`

Если core loop показывает хорошее удержание, тогда продукт можно расширять в сторону:
- coach;
- push;
- subscriptions;
- richer progress layer.

Если core loop не работает, расширение поверх него не решит проблему.
